# 04：三层记忆与偏好规划

## 本篇目标

在原有增量规划和私人 RAG 上补齐近期对话、会话摘要、长期偏好。沿用 Spring Boot、Redis、PostgreSQL，不增加独立记忆服务或画像系统。原文记忆与图范围（1781～4717 行）只提供基础；本次增强依据 [三层记忆设计](../design/待确认-分层记忆与个性化规划设计.md)，不修改原始课程资料。

## 具体业务场景

用户说“以后推荐餐厅尽量不辣，帮我记住”，只保存偏好并回执，不启动旅行规划、追问日期或覆盖最近方案。下次新建行程，默认参考不辣；如果用户说“这次想尝试辣菜”，本次明确条件覆盖默认值，长期档案仍是不辣。

一次对话聊很多轮，较早的“这次带老人，少走路”既可保留在结构化 State，也由摘要压缩成背景。用户说“第二个酒店换一下”，需求分析同时收到近期业务原话和上一轮分支建议，用于定位目标，只重跑住宿。对象不明确就追问，不猜测目标。

## 分步调用流程与入口

1. [ChatServiceImpl](../../src/main/java/cn/zhixing/travel/service/impl/ChatServiceImpl.java) 在原会话锁内验证归属，读取记忆，保存本轮用户原话。认证 userId、操作标识和上下文显式传入 State，不依赖异步线程的 ThreadLocal。
2. [TravelMemoryService.prepare](../../src/main/java/cn/zhixing/travel/memory/TravelMemoryService.java) 读取用户偏好、同会话摘要与近期业务消息。档案读取失败时本轮不注入旧默认值，并明确说明未应用个性化。
3. [RequirementAgent.collect](../../src/main/java/cn/zhixing/travel/agent/requirement/RequirementAgent.java) 仍只做一次需求分析，同时提取本次增量、是否明确记住/忘记、偏好模式及澄清问题。[提示词](../../src/main/resources/docs/sys_agent/RequirementAgent.txt) 禁止从助手、攻略或工具结果推断长期习惯。
4. 只有用户本轮明确要求记住、以后默认或忘记，才调用偏好写入。纯记忆操作走 memoryReply 后结束；正常规划继续合并需求。写入失败不会返回“已记住”。
5. [EffectivePreferences](../../src/main/java/cn/zhixing/travel/memory/EffectivePreferences.java) 保留原始 requirements，另算 effectiveRequirements，按类别整体覆盖。实际交给各 Agent 的 PlannerInput 包含有效条件、相关摘要、近期业务消息及偏好来源。
6. [RequirementChanges](../../src/main/java/cn/zhixing/travel/agent/requirement/RequirementChanges.java) 按有效条件计算交通、住宿、美食的输入指纹。长期偏好变化只有在实际采用时才影响分支；仅更新摘要不会使完整方案重新执行。原有私人资料版本规则继续保留。
7. 模型与工具执行结束后，用短事务复核当前有效偏好并发布助手消息和 latest_plan；模型调用期间不持有档案锁。相关默认值在执行期间变化时返回重新规划提示，不发布过时结果。
8. 每轮业务完成后，达到阈值才尝试一次摘要。摘要失败保留同版本旧摘要与覆盖位置，不阻断已完成的规划。

```text
本轮消息 + 原 State + 长期偏好 + 摘要 + 近期消息
  → 一次需求分析
      ├─ 只记住/忘记 → 校验并保存 → 回执，不写 latest_plan
      ├─ 含义不明 → 澄清，不启动规划
      └─ 正常规划 → 原始条件 + 默认值 → 有效条件与分支指纹
          → 缺项追问 / 局部重跑 / 原结果复用
          → 复核偏好 → 发布完成方案
  → 达到阈值时增量更新摘要（每轮最多一次）
```

## 关键设计和边界

### 三层各存什么

| 层次 | 当前实现 | 默认限制 |
|---|---|---|
| 近期角色消息 | Redis，保留工具请求与结果配对 | 规划角色最多 20 条，7 天 TTL；长角色消息最多保留 6000 字符 |
| 同会话摘要 | PostgreSQL store JSON，按背景/交通/住宿/美食组织 | 保留最近 20 条业务消息；旧消息待处理达到 10 条时触发 |
| 用户长期偏好 | PostgreSQL store JSON，仅交通/住宿/美食 | 每类最多 300 字，只明确保存或面板提交才写入 |

消息条数和字符数都不是 Token 数。摘要每次最多处理 40 条连续老消息，输入最多 12000 字符、输出总计最多约 600 字，均可配置。长消息分段，用 `(memory_seq, coveredOffset)` 表示实际覆盖范围；只有模型返回有效摘要且版本仍匹配时才推进。

SQL 中的业务历史与 Redis 中的角色调用窗口不是同一份消息：前者保留用户原话与最终回复，后者还包含角色输入、子 Agent 回复和工具消息。重新打开会话加载页面历史；再次发消息时，角色窗口如果仍在 Redis 就直接使用，过期或缺失则从 SQL 恢复有效范围内的近期业务消息并缓存。原有每轮 SQL 摘要、近期背景、长期偏好和 State 注入继续保留，因此缓存恢复不是唯一续聊依据。SQL 没保存的旧工具调用轨迹不会伪造恢复。

### Redis 过期后的回填

[PlanningHistoryRecovery](../../src/main/java/cn/zhixing/travel/memory/PlanningHistoryRecovery.java) 还原角色键中的原 sessionId，并校验会话归属、偏好版本和摘要边界。只读取当前有效范围内、最后一条已完成助手回复之前的业务历史；本轮用户问题虽然已经落库，但尚未有回复，不会重复回放。

默认 20 条角色窗口为系统规则、本轮输入和必要的背景头预留位置，最多恢复 17 条业务消息，每条最多保留 1200 字符。更早信息仍靠摘要和结构化 State。截断范围的开头若只有助手回复，会增加明确的历史背景说明，不把这段回复伪装成新的用户要求。

Redis 适配使用带 NX 和 TTL 的原子写入：只在键不存在时发布回填结果，保留 7 天；恢复过程中若其他调用已写入新窗口，就读取那个新窗口，不用旧 SQL 快照覆盖它。没有历史也缓存一次空结果，避免 SDK 在同次调用中反复回源。偏好版本变化或新行程边界不可信时不回放旧背景；回填失败仍可使用原有 SQL 上下文路径继续执行。

```text
再次发消息 → 选择需要执行的 Agent → SDK 读取角色窗口
    ├─ Redis 命中 → 直接使用
    └─ Redis 缺失 → 校验身份、版本与边界 → SQL 近期已完成业务历史
                    → NX + 7 天 TTL 回填 → 系统规则 + 当前输入 → 生成
```

[04-memory.sql](../../src/main/resources/db/04-memory.sql) 为 message 补充数据库生成的 memory_seq，避免用随机 UUID 推断时间顺序；旧数据迁移后的序号用于稳定覆盖，不声称还原所有历史并发消息的绝对先后。偏好、操作回执、摘要继续复用 store，没有新建记忆表。

[RedisChatMemoryStoreConfig](../../src/main/java/cn/zhixing/travel/config/RedisChatMemoryStoreConfig.java) 把 Redis 连接超时与保存期限分开，使用原子带 TTL 写入。本次还修复了旧适配丢弃 SystemMessage 的问题，保留系统规则；窗口裁剪及工具配对交给 SDK。为支持“第二个酒店”的指代，修正原住宿提示词“精选多家但只准三行”的矛盾，改为最多三家、每家三行并带序号。普通对话测试接口不加入三层个性化，窗口大小保持原值；共享存储的 TTL 与系统消息保留修正同样生效。

### 本次条件和长期默认值

| 模式 | 意义 | 例子 |
|---|---|---|
| INHERIT | 本次没有该类显式条件，继承当前默认值 | 平时不辣，本次也参考不辣 |
| OVERRIDE | 本次完整条件覆盖该类默认值 | 本次想尝试辣菜 |
| IGNORE | 本次不使用该类历史偏好 | 这次不参考平时口味 |

默认值不回写原始 requirements。旧检查点里的明确偏好按本次覆盖处理，不反向写长期档案。不把目的地、日期、人数自动存成长久习惯，也不迁移旧 user.preferences 文本。

每个分支指纹只含该分支实际依赖的目的地、时间、人数、全局限制及有效类别偏好；交通还包括出发地。摘要文本不进入指纹，所以更新摘要不会额外重跑。只有显式要求换推荐、真实条件变化、结果缺失或资料版本变化时才重新执行。

### 修改、忘记和隔离

[MemoryRepository](../../src/main/java/cn/zhixing/travel/memory/MemoryRepository.java) 用档案期望版本防止并发覆盖，用操作标识和同事务回执去重。面板与自然语言共用同一服务；不在模型调用期间持有数据库锁，不增加候选审批。

偏好改变后，旧摘要重置到变更前业务消息的当前末尾，只从新上下文继续总结；旧原话不会再被压缩回新摘要。本次单独明确的要求继续留在 State，不因删除长期默认值而被擅自抹除。

[MemoryScope](../../src/main/java/cn/zhixing/travel/memory/MemoryScope.java) 让角色消息范围随偏好版本及新行程换代，避免 SDK 或 Redis 窗口继续带旧偏好。图 threadId 始终是原 sessionId；私人 RAG 从版本化 memoryId 还原原 sessionId，再查服务端会话归属，不会拿 Redis 范围直接查会话。

删除长期偏好不等于删除历史聊天。旧 Redis 范围等待 TTL 过期，旧原话仍可作为业务记录查看，但不会再作为新偏好上下文重新注入。并发发布时依赖短事务复核；同会话执行锁仍只解决单实例并发，没有宣称跨实例互斥。

### 管理入口

页面增加“我的旅行偏好”，提供三个编辑区、清空某类与删除全部。内部版本和存储键不展示给用户。保存不自动改写已经展示的方案，下次规划才按有效输入判断重跑范围。

| 接口（统一前缀 /api） | 用途 |
|---|---|
| GET /memory/preferences | 读取当前认证用户的偏好 |
| PUT /memory/preferences | expectedVersion、operationId、preferences 类别增量 |

自然语言保存或删除后，回执该类别当前完整偏好，用户可以在面板纠正。普通“这次不辣”只作用于本次，含义或类别不明确时先澄清。

## 本篇自查

1. 长期不辣、本次吃辣，哪份数据会改变？
2. 为什么删除档案还要切换消息范围并重建摘要范围？
3. 纯记忆操作为什么不能只凭 missing=false 保存 latest_plan？
4. 摘要失败或长消息只处理一部分，覆盖位置怎么更新？
5. 为什么换了记忆键后私人 RAG 仍能工作？
6. Redis 过期后会重复灌入本轮问题或旧的已忘记偏好吗？

## 自查解答

1. 只更新本次显式条件及有效需求，长期档案不变。只有明确要求长期修改或面板保存才改档案。
2. 否则旧窗口或旧摘要仍可能带回已删除的默认值。新的摘要从新范围建立，本次单独明确的条件继续保留。
3. missing 只是需求完整性；MEMORY、CLARIFY 和 ASK 都不能覆盖完成方案，只有 PLAN 才发布 latest_plan。
4. 失败不推进；部分处理只记录实际完成的序号和字符偏移，后续从剩余部分继续，一轮最多一次摘要调用。
5. MemoryScope 保留原 sessionId，检索器还原后继续验证原会话归属；图 threadId 不变，角色消息键可以独立换代。
6. 不会。SQL 恢复只读有效边界之后、最后一条已完成回复之前的历史，本轮未回复问题不在范围内；偏好版本与摘要边界也会复核，回填后使用 NX 和 TTL 缓存。
